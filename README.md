# Практическая работа № 2. Вариант 17

## Этап 1. Настройки

- Программа на Go, настройки читаются из JSON.
- Проверяются обязательные поля, типы и значения.
- На первом этапе параметры выводились в формате `ключ=значение`.

Настройки в `configs/example.json`:

| Поле | Значение |
| --- | --- |
| `package` | Имя пакета. |
| `repository` | URL реестра npm или путь к тестовому JSON. |
| `test_mode` | `false` — npm, `true` — тестовый файл. |
| `version` | Точная версия пакета, например `4.18.2`. |
| `output` | Имя SVG-файла для этапа 5. Каталог должен существовать. |
| `max_depth` | Глубина обхода; 0 — только корень. |
| `filter` | Подстрока в имени исключаемого пакета; пустая строка — без фильтра. |

Все поля обязательны. Пути в JSON задаются относительно этого файла.
Примеры ошибок для каждого поля находятся в `configs/invalid`.

Нужен Go 1.22+. Запуск и тесты из папки проекта:

```sh
./run.sh
./run.sh --config configs/example.json
./run.sh --test
```

На Windows: `run.bat`, `run.bat --config configs/example.json`, `run.bat --test`.
Без скрипта: `go run ./src`, тесты: `go test ./...`.
Сборка: `go build -o bin/npm-graph ./src`;
на Windows: `go build -o bin/npm-graph.exe ./src`.
Ошибка: `./run.sh --config configs/invalid/package.json`. Справка: `./run.sh --help`.

## Этап 2. Прямые зависимости

- HTTP-запрос к npm registry, разбор JSON средствами Go. npm и Node.js не нужны.
- Получение зависимостей заданной версии: `dependencies` и `optionalDependencies`.
- При совпадении имён приоритет у `optionalDependencies`. Dev- и peer-зависимости не включены.
- Вывод в алфавитном порядке. Обрабатываются ошибки сети, HTTP и JSON.

Проверки:

```sh
./run.sh                                      # express@4.18.2
./run.sh --config configs/no-deps.json         # lodash, нет зависимостей
./run.sh --config configs/scoped.json          # @babel/code-frame
./run.sh --config configs/not-found.json       # отсутствующая версия, HTTP 404
```

Для npm нужен интернет. Таймаут — 15 секунд, лимит ответа — 16 МиБ.
Ошибки выводятся в stderr с кодом 1, успешный запуск возвращает 0.
Автотесты используют локальный HTTP-сервер и работают без интернета.

## Этап 3. Граф зависимостей

- Построение графа рекурсивным DFS. Узлы npm различаются по имени и версии.
- `max_depth` ограничивает глубину: корень — 0, его зависимости — 1.
- `filter` исключает пакеты с указанной подстрокой в имени, с учётом регистра.
  Если исключён корень, граф пустой. Пустой фильтр ничего не исключает.
- Циклическое ребро остаётся в графе и выводится с пометкой `Цикл`.
- Для npm выбирается наибольшая версия по условию зависимости.
  Поддержаны `^`, `~`, сравнения, `||`, wildcard, интервалы, теги и npm-алиасы.
  Git- и file-зависимости пока завершают анализ с ошибкой.
- Результат выводится как список `пакет -> зависимости`, в порядке DFS.
  На границе глубины узел помечается как нераскрытый.

В тестовом режиме сеть не нужна. Формат файла — имя пакета и список зависимостей:

```json
{"A": ["B", "C"], "B": ["D"], "C": ["D"], "D": []}
```

Имена — большие латинские буквы, все зависимости должны быть объявлены.
`version` в этом режиме остаётся обязательным полем настроек, но не используется.

```sh
./run.sh --config configs/test.json           # общий пакет D, порядок A B D C
./run.sh --config configs/test-chain.json     # цепочка A B C D
./run.sh --config configs/test-cycle.json     # цикл A B C A
./run.sh --config configs/test-self.json      # ссылка A на себя
./run.sh --config configs/test-single.json    # пакет без зависимостей
./run.sh --config configs/test-depth.json     # глубина 1: только A, B, C
./run.sh --config configs/test-root.json      # глубина 0: только A
./run.sh --config configs/test-filter.json    # исключён B, остаются A, C, D
./run.sh --test
```

Сейчас `./run.sh` строит весь граф в пределах глубины из настроек.
Вывод только прямых зависимостей остался в коммите этапа 2 (`59e8d8d`).
SVG появится на этапе 5.

## Этап 4. Порядок загрузки

- В JSON добавлен необязательный `load_order`: `true` включает вывод порядка загрузки.
- Зависимости идут раньше использующих их пакетов, общие пакеты не повторяются.
- Учитываются глубина и фильтр. При цикле порядок не строится, возвращается ошибка.

```sh
./run.sh --config configs/order-diamond.json   # D, B, C, A
./run.sh --config configs/order-chain.json     # D, C, B, A
./run.sh --config configs/order-depth.json     # B, C, A (глубина 1)
./run.sh --config configs/order-filter.json    # D, C, A (без B)
./run.sh --config configs/order-single.json    # A
./run.sh --config configs/order-cycle.json     # ошибка: цикл
./run.sh --config configs/order-npm.json       # is-number@6.0.0, is-odd@3.0.1
```

Сравнение с npm 11.12.1 выполнено в отдельной папке с зависимостью `is-odd@3.0.1`:
`npm install --ignore-scripts --no-audit --no-fund --loglevel=silly`, затем `npm ls --all`.
В логе `ADD` сначала `is-number`, затем `is-odd` — порядок и версии совпали.
Метаданные npm запрашивал наоборот: сначала `is-odd`, затем `is-number`,
поскольку зависимости становятся известны после чтения родительского пакета.
Для независимых ветвей возможны разные правильные порядки; npm также использует параллельные операции.
